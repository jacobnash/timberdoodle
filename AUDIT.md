# Timberdoodle — Architecture & Code Quality Audit

**Date:** 2026-09-05 · **Scope:** whole repo (`src/`, `tests/`, `ui/`, `gateway/njs/`, `fantom-his-ext/`; `docs-site/` treated as peripheral — see §2) · **Method:** real tooling everywhere it exists for the ecosystem, manual analysis (explicitly labeled) where it doesn't. Every number below is attributed to the command that produced it.

## Executive summary — the five things that matter most

1. **Zero configured Python lint/type/coverage tooling.** No `ruff`, `mypy`, `radon`, or `coverage` installed or configured anywhere (`.venv`, `pyproject.toml`). This is the single highest-leverage fix — it's what makes everything else in this report a one-time snapshot instead of a standing guardrail. See §4.1.
2. **The 5 stdlib HTTP APIs duplicate ~6% of the Python codebase between them** (`jscpd`, §4.4) — the same span-wrapping/JSON-response/error-handling boilerplate reimplemented independently in `auth_api.py`, `derivation_api.py`, `fault_api.py`, `ingest_api.py`, `validate_api.py`. Real, fixable, and fixable without touching the deliberate "no framework" decision. See Theme A.
3. **A live, reproducible gap between the documented gateway-restart workaround and reality**, discovered by literally running `docker compose up -d` and the test suite (not a contrived scenario) — 3 test failures + 8 errors, all fixed by `docker compose restart gateway`. Sharper than what `CLAUDE.md` currently documents. See Theme B.
4. **100% line coverage on `mapping.py` still misses real behavior**: `mutmut` found 96 surviving mutants in `classify_point`/`load_rules`, including one where deleting the `rules = load_rules()` default-fallback entirely still passes every test. Coverage % is not a proxy for test quality here. See Theme C.
5. **One real, unhandled-`None` bug**: `llm_classifier.py:76-78` accesses `response.parsed_output.brick_class` etc. without checking for `None`, which the Anthropic SDK's own types allow (`mypy`, confirmed by reading the SDK call). See Theme D.

Also good to know up front: **the architecture itself is sound and mostly not the problem.** Complexity is low (`radon`: average cyclomatic complexity 2.7, nothing above CC 18, all files maintainability-index grade A), there's no significant dead code, DIT/NOC is a non-issue (no real inheritance beyond stdlib handler subclassing), and one design decision that looked like a risk on paper (`json_store.py`'s no-file-locking JSON config store) turned out to already be a deliberately reasoned, documented tradeoff with atomic writes already in place. Don't refactor what isn't broken — see §6.

## 1. Ground truth

### Intended architecture (from `docs-site/pages/architecture.mdx`, `README.md`, `CLAUDE.md`)

Timberdoodle is an "ontology-agnostic building data platform": Oxigraph/SPARQL holds entity identity, tags, and relationships (Brick/Haystack/DBO loaded at runtime, not baked into code); Postgres/TimescaleDB holds time-series so any SQL tool (Grafana) reads it natively — the two stores are deliberately kept separate. Every service is an independently-buildable/restartable Docker container from one shared image, differentiated only by `docker-compose.yml`'s `command:`. All 5 HTTP APIs (`auth_api`, `ingest_api`, `fault_api`, `derivation_api`, `validate_api`) use stdlib `http.server.ThreadingHTTPServer` directly — a framework was explicitly rejected as unneeded weight for a handful of routes each. Dual ingest front doors (MQTT via `mqtt_listener.py`, HTTP via `ingest_api.py`) funnel into shared `ingest.py` functions — single write path. Fault detection (`fault_api.py` CRUDs `rules.json`; `fault_detector.py` is the sole evaluator) and derivations (`derivation_api.py`/`derivation_engine.py`) both use an API/engine split coupled only through JSON config files + MQTT, reasoned as intentionally low-coupling. An nginx gateway with `njs` modules (`gateway/njs/{policy,jwt,ratelimit,main}.js`) is the sole external entry point, doing JWT auth/policy as defense-in-depth, explicitly not a substitute for per-service checks.

### Actual structure

Confirmed to match the above. 34 files in `src/timberdoodle/`: 5 HTTP APIs, 8 daemons/pullers (`mqtt_listener`, `fault_detector`, `derivation_engine`, `haystack_puller`, `sql_puller`, `energystar_puller`, `openmeteo_puller`, `ui_server`), 21 shared libraries. `docker-compose.yml` wires infra (postgres/timescale, oxigraph, mosquitto, jaeger, grafana) and gates 4 pullers behind compose `profiles`. `ui/` is deliberately buildless vanilla JS/HTML/CSS (no `package.json`, by design, per file comments). `gateway/njs/` has its own hand-rolled `node`-runnable self-checks. `fantom-his-ext/` is a small Haxall pod extension (4 files, 227 lines).

### Where intent and reality diverge — none structurally

No architectural drift was found: the stdlib-http-per-service pattern, the JSON+MQTT coupling, and the RDF/timeseries split are all implemented as documented. The gaps that exist are **already tracked by the project itself** (§5) or are the concrete findings in §4/§6 below — there is no "the docs say X but the code does Y" surprise at the architecture level.

### Ecosystem idiom note

This is a small (~5.1k LOC `src/`, ~5.5k LOC `tests/`, ~1.2k LOC `ui/`, ~320 LOC `gateway/njs/`, ~227 LOC Fantom), early-stage (15 total commits), largely solo/AI-assisted codebase. Findings below are calibrated to that reality — e.g., DIT/NOC and mutation-testing-at-scale are reported once and not treated as ongoing gates, per §2.

### 4.2 Coupling, cohesion, SOLID, cross-cutting structure (manual, no tool exists for this ecosystem/scale)

- **DIT/NOC**: `grep -n "class .*(" src/timberdoodle/*.py` shows inheritance is limited to each API's own `BaseHTTPRequestHandler` subclass (one per file: `AuthHandler`, `DerivationHandler`, `FaultHandler`, `IngestHandler`, `ValidateHandler`) plus test doubles. Depth of inheritance tree is 2 everywhere it exists. **Non-issue, reported once.**
- **Cohesion (LCOM)**: no Python LCOM tool exists at this scale, checked by hand instead. Each `*Handler` class is built by a closure factory (`fault_api.py:55-56`: `def make_handler(rules_path, webhooks_path, ts_pool): class FaultHandler(BaseHTTPRequestHandler): ...`) — the shared values are captured **by closure, not stored as `self.` instance attributes**, so there's almost no instance state for methods to (dis)agree on; classic LCOM barely applies to this shape. The real cohesion question is whether the bundled routes belong together: yes, mostly — each route method delegates immediately to a single-purpose module function (`list_faults`, `ack_fault`, `enable_webhook`, etc. in `faults.py`), so the handler classes are thin routing shims, not where the logic (or the cohesion risk) actually lives. `FaultHandler` does bundle two related-but-distinct sub-concerns (fault-rule CRUD + webhook-subscription CRUD) — worth watching if webhooks grow into their own concern, not worth splitting today.
- **Route count per API file** (rough SRP signal — routes handled per file, via `grep -c "elif self.path\|if self.path\|re.match"`): `fault_api.py` 10, `ingest_api.py` 8, `derivation_api.py` 7, `validate_api.py` 3 (`auth_api.py` uses a different dispatch shape, not counted by this grep). 200-300 lines and 3-10 routes per file — no god-module signal.
- **Connascence via shared JSON config** (`rules.json`, `derivations.json`, `webhooks.json`, all through `src/timberdoodle/json_store.py`): read in full. This is **already a deliberately reasoned, documented tradeoff**, not a silent gap — see §6 (leave alone).
- **SOLID, per letter**:
  - **S (SRP)** — clean at both the file level (one file = one bounded API/concern) and function level (handlers are thin, logic lives in single-purpose modules). No violation found.
  - **O (OCP)** — real but mild: `fault_detector.py:245-247` (`if rule["type"] == "stuck": ... elif rule["type"] == "stale":`) and `derivation_engine.py:269` (`kind == "rollup"` vs. formula) are both type-dispatch that requires editing existing code to add a new rule/derivation kind. Only 2 known variants each today with no near-term third — a strategy/registry pattern here would be speculative generality (YAGNI). **Leave alone; revisit only if a 3rd variant is actually added.**
  - **L (LSP)** — not really applicable; the only inheritance is each API's single `BaseHTTPRequestHandler` subclass (depth 2), no narrowed preconditions or sentinel-return overrides observed.
  - **I (ISP)** — not applicable; no interfaces/ABCs exist in this codebase (Python, duck-typed throughout).
  - **D (DIP)** — technical violation, no real pain: API modules (`fault_api.py`, etc.) import concrete `timeseries.connect_pool`/psycopg directly rather than through an abstraction. Postgres/Timescale is a deliberate, documented, non-swappable architectural choice (§1), not a "might switch someday" — an abstraction layer here would itself be speculative generality. **Leave alone.**

## 6. Themed findings

### Theme A — Duplicated request-handling boilerplate across the 5 stdlib HTTP APIs
**Severity: medium · Effort: S**
Each of `auth_api.py` (`_handle`, line 51), `derivation_api.py` (`_handle`, line 126), `fault_api.py`, `ingest_api.py` (inline per-route, e.g. line 74), and `validate_api.py` (inline, line 47) independently reimplements: a `tracer.start_as_current_span(name)` wrapper, a try/except that sets `span.set_attribute("error", str(exc))`, a JSON-response helper, and a `log_message` override. `jscpd` (§4.4) confirms this is the single largest concentration of Python duplication in the repo (15 of 50 clone pairs). **Cost:** a bug fixed in one API's error-handling path (e.g., a missing `Content-Type` header, a span-attribute typo) has to be independently re-fixed in the other four; a new API author will copy-paste the pattern a sixth time. **Fix respects the existing architecture**: extract a small shared module (e.g. `http_handler_base.py`) that each service still imports independently and instantiates as its own `ThreadingHTTPServer` — this removes the duplication without adopting a framework, which the project has explicitly and reasonably declined.

### Theme B — Gateway upstream-address caching: live-reproduced, and easier to trigger than documented
**Severity: high · Effort: S (doc fix) / M (real fix)**
`CLAUDE.md` already documents that restarting a single backend container without restarting `gateway` causes 404/502s. This audit hit the *same* failure mode (3 test failures, 8 errors, all `502 Bad Gateway` from `auth_api` routes through the gateway) from a **plain `docker compose up -d`** — the exact command the README's quick start tells a new user to run — not an atypical independent-restart workflow. `docker compose restart gateway` fixed it immediately (verified: 11/11 previously-failing tests passed after the restart, full suite went from 3 failed/8 errors to 0 failed). **Cost:** a first-time user following the documented quick-start can hit a wall of 502s with no indication why, and existing docs frame this as an edge case rather than something the standard startup path can trigger. **Fix options** (framed as tradeoffs for Stage 3, not decreed): (a) cheapest — update `README.md`'s quick-start to always include `docker compose restart gateway` as the last step; (b) real fix — have `gateway`'s `njs` resolve upstreams per-request via the existing `resolver 127.0.0.11` mechanism already used elsewhere (per `CLAUDE.md`'s own njs gotchas) instead of caching at startup.

### Theme C — Coverage percentage doesn't mean what it looks like it means here
**Severity: medium · Effort: S**
`mapping.py` shows 100% line coverage in `pytest-cov`, yet `mutmut` found 96 surviving mutants there, including one (§4.6) where the documented `rules=None` → `load_rules()` fallback can be deleted entirely without failing a single test. Separately, `autotag.py:run` (CC 16, the entire retry/classification/rule-proposal driver) is only 34% covered — the more common and more actionable version of this problem (low coverage, not just low mutation-kill-rate). **Cost:** the fallback-path gap in `mapping.py` means a real regression there (e.g., `classify_point` silently never calling `load_rules()` when it should) would ship undetected; `autotag.py`'s untested retry loop is the more likely place an actual outage-handling bug lives undetected today. **Fix:** targeted test additions (Stage 0/1 material, see PLAN.md) — not a broad "increase coverage" mandate, since `webhooks.py`'s 100%-covered, 0-surviving-mutants result in the same pass shows the codebase is capable of genuinely well-tested modules.

### Theme D — Unhandled `None` from the Anthropic SDK's structured-output parsing
**Severity: medium · Effort: S**
`llm_classifier.py:76-78`: `response.parsed_output` is typed as optional by the SDK (parsing can fail to produce a valid structured object), but the code accesses `.brick_class`, `.confidence`, `.reasoning` on it directly with no `None` check, confirmed by `mypy` (`union-attr` error) and by reading the call site. **Failure scenario:** the LLM ever produces output that the SDK can't parse into `_ClassificationSchema` (malformed JSON, missing field, safety refusal) → unhandled `AttributeError` crashes the `autotag.py` classification loop for that point, and (per Theme C) this path has no test coverage to catch a regression. **Fix:** a `None` check with a clear "classification failed, skip/retry" path — small, local, no design decision needed.

## Explicitly-fine — reviewed and left alone

- **`json_store.py`'s no-file-locking JSON config store.** On paper this looked like the audit's most interesting connascence risk (shared mutable JSON config across processes). Reading the module found it's already a documented, reasoned decision: single-writer-per-file is the actual usage pattern (`rules.json`/`webhooks.json`/`derivations.json` are each written by exactly one process), the module's own docstring states the tradeoff explicitly ("known, accepted gap... fine per YAGNI unless multi-process writes are actually needed"), and writes are already atomic (temp file + `os.replace`). Nothing to fix here — this is the rubric's "pragmatic violation with a clear reason" case.
- **mypy's `faults.py:176` / `derivation_health.py:45` "indexing a possibly-`None` tuple" errors.** Both are `INSERT ... ON CONFLICT DO UPDATE ... RETURNING ...`, which is structurally guaranteed to return exactly one row — `mypy`/`psycopg`'s typing just can't express that SQL guarantee. Not a bug; not worth a `# type: ignore` churn pass either given the other 17 mypy errors are more informative.
- **`ruff`'s `BLE001` (blind `except Exception`) hits in the pullers** (`haystack_puller.py`, `sql_puller.py`, `openmeteo_puller.py`, `energystar_puller.py`): each catches broadly around a single external-API call inside a polling loop specifically so one bad poll doesn't kill the daemon — a defensible pattern for a long-running poller talking to unreliable external systems, *provided* the exception is logged (it is, in all four, via `print(...)` with the exception included). Flagged in §4.1 for completeness, not escalated to a Theme.
- **The stdlib-`http.server`-over-framework decision itself.** Duplication exists (Theme A) but the underlying architectural choice is sound for 5 services at ~200-300 lines each; the fix is a shared helper, not a framework migration.
