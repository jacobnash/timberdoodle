---
title: Multi-Site & Campus
---

**Status: design decision, not implemented.** No second site or command
channel exists in this repo today — this page records the reasoning so it
doesn't get re-litigated (or re-guessed) later. Everything below either
cites code that exists now, or is explicitly marked as not built yet.

## Site as data, not as infrastructure

Nothing in the data plane knows about "sites" today. `auth_api.py` has an
org → sites model (`POST /sites`, users/API keys carry `site_ids`), but
that's an authorization scope only — `site_id` appears nowhere else in the
codebase. `point_history` has no site column, and point identity is a flat
`urn:point:{topic}` namespace (`ingest.py`).

That flat namespace is actually the reason a campus rollup doesn't need new
infrastructure. Point and equip identity are derived straight from the MQTT
topic string, and per [FBF](/fbf)'s own wire contract the topic is
`f"{topic_prefix}/{point}"` — `topic_prefix` already varies per FBF
instance (e.g. `fbf/mock-ahu-1/...`). Point two FBF instances at two
buildings at the same shared `mosquitto`/`mqtt_listener`/Postgres/Oxigraph
stack, give each a distinct `topic_prefix` (e.g. `fbf/hospital-a/...` vs
`fbf/hospital-b/...`), and their points/equipment never collide — no
migration, no new column, because identity was never global to begin with.

For campus-level filtering ("all faults across sites," "just Site B"),
tag each equip with a `site` Haystack tag through the ingestion path that
already exists (`ingest_tags`/`ingest_equip_tags` in `ingest.py` take an
unconstrained tag dict). `site` is then just a queryable property in
Oxigraph like any other tag — no new mechanism.

This only holds if sites can share one Postgres/Oxigraph. If a site must
stay data-sovereign or run standalone when disconnected, it needs its own
full stack, with the central campus stack pulling from it — the same
pull shape `haystack_puller`/`sql_puller` already implement, just pointed
at a peer Timberdoodle instead of a third-party source. That's a bigger
decision than this page covers and hasn't come up yet.

## Why not a mesh network

This came out of pulling apart `arcbeam.pod`, a commercial (non-AFL)
binary SkyFoundry ships inside the otherwise open-source Haxall release.
It's a WebSocket-based mesh: every `Node` gets a keypair identity, `Hub`
tracks `Chan`s, `NodeType` spans SkySpark hosts, SkySpark projects,
Niagara, Haxall, and edge node types (NanoEdge, SteelBeam, XetoBase) that
can apparently all talk to each other, not just up to one central point.
`ConnChan` exposes a full remote-RPC surface (`readAll`, `pointWrite`,
`watch`, `eval`, `hisRead`) across that mesh.

Timberdoodle's topology is a star, not a mesh: N sites report up to one
gateway/broker/store, and sites never need to talk to each other. A star
doesn't need peer identity, routing, or an RPC surface between leaves —
a plain broker's client/hub model already covers everything a star
topology requires. Building mesh machinery (keypairs, signed frames, a
node-type registry) for a topology that's provably a star is solving a
problem this system doesn't have.

The one property worth taking from arcbeam is that it's WebSocket
(outbound-initiated, so it doesn't fight building-network firewalls) —
and MQTT already has that property. Once an MQTT client opens its session
to the broker, either side can send over it; the broker never needs a
route back into the site's network. That's the same trick, using
infrastructure already in this stack, for the one topology this system
actually has.

## Reaching back into a site: commands, not just ingest

FBF already has a real REST surface for exactly the kind of thing you'd
want to trigger remotely — `POST /discover`, `POST /learn`, `POST
/modbus/discover` (takes a CIDR), device/credential management (see FBF's
own `docs/bacnet-discovery-api.md` and
`docs/periodic-discovery-and-credentials.md`). The gap isn't capability,
it's reachability: that server binds inside the building, and a central
Timberdoodle has no inbound path to it, especially on a network that can
only originate connections outward and never receive them.

Design (not built): give `fbf.api` a command-topic subscription —
`cmd/{site}/{instance}/#` — on the same MQTT connection it already holds
open to publish readings. A command message (e.g.
`{"action": "modbus_discover", "cidr": "10.2.0.0/24"}`) gets dispatched
in-process to the same handler its own `POST /modbus/discover` route
already calls. No new server, no new port, no firewall exception —
it rides the identical egress rule that already lets FBF publish
telemetry today, because it's the same connection.

Two things this needs to be safe once it controls real scans, not just
telemetry:

- **Persistent session** (`clean_session=False`, QoS 1) on FBF's
  subscribe, so a command sent while the site is offline is queued by the
  broker instead of dropped.
- **Per-site broker ACLs.** `mosquitto`'s config in this repo has no
  auth/ACL today, which is fine for one trusted network. Once a command
  channel can tell FBF to scan a subnet, a client needs to be restricted
  to its own site's topic prefix (`cmd/{its-own-site}/#`) — otherwise a
  compromised or misconfigured client at one site could trigger scans at
  another.

## MQTT has zero delivery guarantee today

This matters more once sites are remote and links aren't as reliable as
one Docker network — worth being precise about, because the current
answer is worse than "a small buffer," it's no buffer at all:

- `fbf/src/fbf/mqtt_sink.py`'s `publish_reading()` calls
  `client.publish(topic, payload, retain=True)` with no `qos` — paho-mqtt
  defaults to **QoS 0**, no ack, no retry, nothing queued for an offline
  subscriber by default.
- `mqtt_listener.py`'s client never sets `clean_session=False`, so even
  raising QoS wouldn't help — mosquitto only queues messages for a
  session it's been told to remember across disconnects.
- `retain=True` is not a history buffer. It caches the single *latest*
  value per topic for new subscribers — a thousand readings during an
  outage still leave exactly one value cached, the rest were never
  written anywhere.
- `mosquitto` runs as `mosquitto -c /mosquitto-no-auth.conf` (the image's
  built-in default, no mounted config, no `persistence true`) and FBF's
  publish path has no on-disk spool of its own.

Net effect: a link drop between a site and the broker is a clean gap in
`point_history` for every point on that link, for the full outage —
nothing partially survives to lose.

The cheap, honest comparison: `clean_session=False` + QoS 1 on both ends
gets mosquitto's *default* `max_queued_messages` of 1000 per client —
not unlimited, and 1000 messages across a busy multi-point site can
still blow through in well under 12 hours. But 1000 is a real number
above zero, which is what a Haxall/SkySpark-side connector doing the
equivalent job with any store-and-forward buffering would already give
you, and this stack currently gives none. That gap is a legitimate point
in Haxall's favor as shipped, not a wash — worth fixing (raise the queue
cap, turn on persistent sessions, and if the BACnet/Modbus devices keep
their own trend logs, backfill from those on reconnect instead of trying
to make MQTT itself lossless) rather than waved off as equivalent.

## When mesh-style networking would actually be justified

If Timberdoodle deployments themselves needed to federate — separate
orgs, data-sovereignty requirements forcing separate stores — *and* those
deployments needed to query or command each other live, not just roll up
for viewing, that's closer to what arcbeam actually solves. That's a
stronger requirement than campus aggregation and isn't implied by
anything on the roadmap today; if it shows up, revisit this page instead
of quietly reinventing arcbeam.
